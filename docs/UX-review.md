# XEvents user journeys

The UX review covers the bot and Mini App together. Behaviour is verified with automated bot tests, Worker integration tests using a mocked Telegram API, and a local browser preview. Actual mobile Telegram rendering, real payments and notification delivery on a user's device require a live device check.

| Journey | Expected behaviour |
| --- | --- |
| Create in chat | Show **🎉 Create event** in the bot's main menu. Collect a title, button-selected date and time in a visible timezone, and a location or later choice, then offer Review/Create. Use the saved timezone when available and explicitly show UTC otherwise. Keep optional settings under More options, accept custom dates/times, and reject stale wizard buttons. Creation works without opening App; ordinary text supplies the title, address and guest names. |
| Create or edit | Event type offers Ticket booking — Private, Named invitations — Private and Public event. Public enables Explore discovery in the event's timezone and uses ticket booking; the separate visibility control is removed. Existing public bookings load correctly, and older RSVP events keep their mode, links and responses through visibility changes. Co-hosts may change visibility without changing the invitation mode. Existing details and banner load when editing. Add named guests individually with name, 1–10 attendee count and a plain-language count rule, or use the bulk text list. Individual additions append to the current draft; duplicate names, malformed names and invalid counts cannot overwrite it. Phone sharing, comments and media extras default off. Hidden payment fields do not block a different payment method. |
| Ticket link | Show booking or ticket request actions; collect the guest's name. No RSVP choices. |
| Named invitation | Use the organiser's guest name; show Accept, Reject, Maybe and Respond later, including any response deadline. One-time links default on for named lists: the first completed Accept, Reject or Maybe response locks the link to that Telegram account. Opening it or choosing Later first does not consume it. The same account can revise its response before the deadline; forwarded links are blocked after locking. Turning one-time use off allows multiple accounts to use the link. |
| Group size | Ticket mode can enable a group-size question. Named invitations use each guest's count setting: `Alex = ?` asks, `Alex = 2!` confirms two places, `Alex = 2` uses two with a current-count change button, and `Alex = 2*` fixes two with no question or change option. A bare name means one person. Reserved counts are bold; editable buttons say, for example, **2 people · Change**, and follow the selected count. Counts include the guest and are limited to 1–10. |
| Copy personal invitations | Manage → Invitation links shows ten guest-name buttons per page in two columns. Copy the complete invitation and personal link directly when within Telegram's copy limit; otherwise open the selected guest in App for an explicit copy gesture. Without App, show full text and sharing. Clipboard denial exposes selectable full text; private locations are omitted from shared text. |
| Manage personal invitations | Show response details and attendee totals alongside personal links. Combine response filters with name search, including multiple responses on reusable links. Add guests individually or in bulk without replacing existing links; preserve unrelated drafts. Guest list shortcuts open additions or the exact personal invitation identified by its response account, even when display names overlap. Revoke opens Notify guest, Remove silently or Keep invite; notification is unavailable without a linked Telegram account. Shared ticket rosters omit named-invitation controls. Removal invalidates the link and ticket and clears associated responses, reminders and response sessions while retaining payment records. Current host permissions and version checks reject stale changes; retries do not duplicate additions or notifications. |
| Co-host access | Create multiple optionally labelled one-use links. The owner sees each claimant's Telegram name, handle and ID, and can cancel or revoke one entry without changing the others. Current role checks reject revoked access; stale confirmations cannot revoke a changed entry. Existing guest responses and tickets survive role changes. |
| Save RSVP | Remove buttons from the tapped message, save the response and notify the organiser. Phone sharing and comments appear only when enabled; custom guest questions are not part of the flow. Named RSVPs save without organiser approval. Repeated or stale taps cannot replace a newer response or reset a ticket request's approval. |
| Respond later | Show unanswered RSVP invitations. Ticket booking links are excluded. Hide Pending when there are none. |
| Approval | In ticket-booking mode, notify the guest on approval or rejection. Approval buttons refer to a particular response version; an older request cannot approve a newer response. Named invitations have no organiser approval setting. |
| Private information | Keep restricted location and ticket details locked until the required acceptance, ticket-request approval and payment steps are complete. A named invitation can withhold its location until acceptance and any required payment without adding an approval step. |
| Accepted guest | Show Change response and organiser-enabled extras. Shared media stays among the main event actions. |
| Payment | Stars confirmation requires Telegram's successful-payment update. Manual payment reports require organiser verification; reporting does not unlock tickets. A payment report under review cannot be replaced by a new RSVP. |
| Media-only link | Show the banner, title and permitted media actions without RSVP. Saving or sending files remains explicit. Gallery refreshes cannot overwrite a newer request. |
| Reminders | Default reminders wait for a confirmed acceptance, including approval and payment. Send once per event start time. Personal overrides remain available to accepted guests. |
| Cancel or delete | Owners see Cancel event and Delete event in a red edit-page section. The three-dot menu offers one Cancel event action; its confirmation optionally deletes after cancellation through a single request. Notify accepted and tentative guests, clear the stale editor, remove the event from My events, and preserve payment records needed for refunds. Failed requests keep the confirmation open for an explicit retry. |
| Navigation and errors | Home has app event details, editing and guest-management shortcuts, with a separate chat action and media/ticket buttons when permitted. My events actions use consistent icons and two-column buttons, with a full-width chat action; every three-dot action has an icon. The Telegram keyboard has Create event, My events and Help, with App available through the built-in menu; contextual app links remain. Advertise only Help, Cancel input and Payment support commands, while preserving old handlers and deep links. Prevent duplicate async button actions. Show actionable errors inside the Mini App. |

Clicked messages lose their buttons. Other previously delivered messages cannot all be edited retroactively; new RSVP and approval messages contain response versions, so stale actions are rejected when tapped. Older messages from before version tracking still use legacy validation.

Startup errors remain visible and copyable without exposing hosting addresses, launch data or credentials. Runtime diagnostics include a known public script name and line number when the browser provides them; masked external-script errors explain that details were withheld. Telegram's SDK loads with anonymous CORS so supported clients can report the underlying exception. Optional ready, expand and theme-subscription bridge failures are reported independently and do not stop event-data loading.

A one-time link stays locked when its holder later chooses Respond later. Shared ticket-booking links default to reusable, with an optional one-time setting. Enabling one-time use is rejected if the affected link already has final responses from multiple accounts. A personal link identifies the first responding Telegram account, not a verified real-world identity, so organisers should send it privately to the intended guest.
